1. PROJECT OVERVIEW (ELEVATOR PITCH)
--------------------------------------------------------------------------------
Project Name: Student Organization System (Skyline Student Association / ODDO)
Purpose: A complete full-stack web application designed for student club 
operations, ticketing, memberships, merchandise sales, and event check-ins.

Core Modules:
- Authentication & Sessions:
  PostgreSQL-backed sessions, role-based access control (member, organizer, 
  treasurer), secure password hashing (argon2/bcrypt).
- Membership Management:
  Online enrollment, dues tracking (active, pending, expired), and member 
  directory for organizers.
- Event Ticketing & Capacity:
  Public event discovery, organizer event creation/updates, ticket generation, 
  and capacity reservation protected by atomic database locks (FOR UPDATE).
- Check-in System:
  Token/QR-based ticket validation with atomic one-time check-in checks to 
  prevent duplicate entry.
- Merchandise Store & Ordering:
  Product catalog, cart management, inventory deduction with deadlock-safe 
  variant locking (ORDER BY id ASC FOR UPDATE), order lifecycle tracking.
- Manual Payment Recording:
  Dedicated dashboard for treasurers/organizers to record offline cash/UPI 
  payments with idempotency key protection.

Tech Stack:
- Frontend: React 18, Vite, React Router v6, Context API (AuthContext, 
  CartContext), Vanilla CSS with centralized design tokens.
- Backend: Node.js, Express.js REST API, PostgreSQL (pg connection pool), 
  Joi input validation schemas, Express session middleware.

3. FOUR-STEP ACTION PLAN FOR ANY CHANGE REQUEST
================================================================================
When the coordinator or team asks you to modify something:

STEP 1: CLASSIFY THE SCOPE
- UI/Styling only: Colors, layout, typography, responsiveness.
- Frontend Logic: React component state, forms, API fetch hooks, routing.
- Backend API/Logic: Endpoint route, validation rule, business logic in service.
- Full-Stack: Adding a new field from database -> API response -> React screen.

STEP 2: LOCATE THE RIGHT FILE USING TAGS OR PATHS
(Search tags from docs/QUICK_CHANGE_GUIDE.md using Ctrl+Shift+F):
- Navbar Colors / Theme:     @edit:NAVBAR_COLORS   -> client/src/styles/tokens.css

- Navigation Links:          @edit:NAVBAR_LINKS    -> client/src/config/navigation.js

- Cart & Checkout UI:        @edit:CART_UI         -> client/src/pages/shop/CartPage.jsx

STEP 3: MAKE THE CHANGE (FOLLOWING ESTABLISHED PATTERNS)
- Frontend: Use CSS tokens (var(--primary), var(--text-color)) instead of 
  hardcoding arbitrary hex codes.
- Backend: Always validate client inputs with Joi schemas in server/validators/ 
  before passing data to services.
- Error handling: Keep standard JSON responses { data: ... } or { error: ... }.

5. SELF-TEST QUESTIONS & ANSWERS (TEST YOURSELF)
================================================================================

QUESTION 1:
Where do you change the navigation bar items (labels and URLs)?
ANSWER:
In `client/src/config/navigation.js`. The component `Navbar.jsx` imports links 
from this config file.

QUESTION 2:
Where are the backend route endpoints registered into Express?
ANSWER:
In `server/app.js`. It mounts routes under `/api/v1` such as `eventRouter`, 
`memberRouter`, `checkinRouter`, and `merchandiseRouter`.

QUESTION 3:
How does the backend prevent overbooking an event when two users click "Register" 
at the exact same second?
ANSWER:
In `server/services/event.service.js` and `server/model/event.model.js`, it uses 
a PostgreSQL transaction with a row-level lock (`SELECT ... FOR UPDATE`). 
Only one transaction can inspect and increment the seat counter at a time, 
preventing race conditions.

QUESTION 4:
How does the merchandise checkout avoid deadlocks when customers buy multiple 
items simultaneously?
ANSWER:
In `server/model/merchandise.model.js`, the query locks variant rows sorted 
by ID in ascending order (`ORDER BY id ASC FOR UPDATE`). Because all concurrent 
transactions acquire locks in the exact same sequence, deadlocks are avoided.
