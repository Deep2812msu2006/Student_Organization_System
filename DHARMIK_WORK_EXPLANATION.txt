A. TICKET CHECK-IN SYSTEM (Step 5 — PR #6)
--------------------------------------------------------------------------------
• Frontend Screen: /staff/checkin (CheckInPage.jsx)
  - Designed for door staff and organizers.
  - Manual entry of 16-character admission tokens (e.g., sky1_...).
  - Real-time attendance counters and immediate success/denial feedback.
  - Fully accessible (aria-live announcements, keyboard navigation).

• Backend Service & API:
  - POST /api/v1/checkins
  - GET /api/v1/events/:eventId/attendance
  - Rule @rule:CHECKIN_ONCE: Single conditional atomic SQL update:
    UPDATE registrations SET checked_in_at = now() 
    WHERE event_id = $1 AND token_hash = $2 AND status = 'confirmed' AND checked_in_at IS NULL;
  - Zero Race Conditions: If two door staff scan the same ticket simultaneously, exactly one succeeds; the second receives an explicit duplicate scan denial.
  - Security: Stored token hashes (SHA-256) are used; raw ticket secrets are never persisted or exposed.

B. EVENT MANUAL PAYMENT CONFIRMATION (Step 5 — PR #6)
--------------------------------------------------------------------------------
• Frontend Screen: /staff/payments (PaymentPage.jsx — Event Registrations tab)
  - Labeled "Record manual payment received" (cash, UPI, bank transfer).
  - Explicitly non-gateway: does not collect card numbers or simulate a fake payment gateway.

• Backend Service & API:
  - POST /api/v1/payments/manual
  - GET /api/v1/events/:eventId/pending-registrations
  - Transaction Safety: BEGIN -> lock event row -> check allocation -> insert durable row into payment_records -> update registration status pending -> confirmed -> COMMIT.
  - Idempotency: Idempotency-Key header is enforced. Replaying an identical request returns 200 with the original payment evidence. Changing the payload returns 409 conflict.
  - Zero-price tickets: Handled honestly via method 'zero_price' and amount 0.

C. MERCHANDISE MANUAL PAYMENT CONFIRMATION (Step 7 — PR #10 & Current Branch)
--------------------------------------------------------------------------------
• Frontend Screen: /staff/payments (PaymentPage.jsx — Merchandise Orders tab)
  - Paginated list of pending merchandise orders awaiting settlement.
  - Snapshot summary showing buyer contact and snapshotted line items.
  - Confirmation modal capturing payment method (cash/UPI/wire), external transaction reference (UTR/receipt #), and notes.
  - Idempotency key generated once upon opening modal and preserved across network retries.

• Backend Service & API:
  - GET /api/v1/orders/pending & GET /api/v1/staff/orders/pending (paginated, internal keys sanitized).
  - POST /api/v1/payments/merchandise/manual
  - Strict Authorization: Explicitly permits 'treasurer' and 'organizer' roles. Ordinary members and volunteers are strictly rejected (403 FORBIDDEN).
  - Rule @rule:ORDER_LOCK_ORDER: Locks the order row first (SELECT ... FOR UPDATE) matching cancelOrder lock order to guarantee zero deadlocks.
  - Rule @rule:PAYMENT_TARGET_MUTEX: Enforces that each payment record points to EITHER registration_id OR order_id, never both and never neither.
  - Rule @rule:PAYMENT_ONCE: Conditional status update pending -> paid with paid_at timestamp.
  - Advisory Locks: Scoped key transaction lock (pg_advisory_xact_lock) serializes simultaneous duplicate requests.
  - Stock Invariant: Stock is NOT deducted again during payment (stock was already deducted atomically upon order placement by Om's order service).

3. FREQUENT COORDINATOR / INTERVIEW QUESTIONS & MODEL ANSWERS
--------------------------------------------------------------------------------

Q1: "Why do you have manual payment recording instead of integrating Stripe/Razorpay?"
A1: "In student organizations and campus clubs, many transactions occur offline via cash at club desks, direct UPI/bank wire to the university treasury account, or fee waivers. Our system models this reality with an audited manual confirmation flow by authorized treasurers. We capture durable audit evidence (receipt #, UTR, staff ID, timestamp) into the payment_records table. A real payment gateway can easily be plugged in later by calling the exact same payment confirmation service."

Q2: "What prevents double-spending or duplicate payment confirmations?"
A2: "Three distinct layers of protection:
 1. Scoped Idempotency Keys: Every confirmation request requires an Idempotency-Key header scoped to the treasurer. Identical retries safely return 200 with the original payment.
 2. PostgreSQL Transaction Advisory Locks: pg_advisory_xact_lock serializes simultaneous identical requests so they don't race.
 3. Database Constraints & Atomic Conditional Update: payment_records has a UNIQUE index on order_id, and the status transition executes UPDATE orders SET status = 'paid' WHERE id = $1 AND status = 'pending'. If two requests race, exactly one wins; the second affects 0 rows and returns 409 ALREADY_PAID."

Q3: "How did you prevent deadlocks between payment confirmation and order cancellation?"
A3: "We enforced Rule @rule:ORDER_LOCK_ORDER. Both cancelOrder and confirmMerchandisePayment lock the exact same orders table row first using SELECT id, status FROM orders WHERE id = $1 FOR UPDATE. Because both transactions acquire locks on the same resource in the same sequence, deadlocks are mathematically impossible. Whichever transaction acquires the lock first executes, and the second observes the updated state."

Q4: "What happens if a customer tries to cancel an order after the treasurer confirms payment?"
A4: "Customer cancellation is governed by Rule @rule:PENDING_ONLY_CANCEL. 
 On the frontend (OrderDetailPage.jsx), the cancellation button is only rendered if status === 'pending'.
 On the backend (merchandise.service.js & merchandise.model.js), if status is 'paid', the cancellation is rejected with HTTP 409 CANNOT_CANCEL. This prevents inventory stock restoration on items that have already been paid for."

Q5: "Who is authorized to confirm payments and check in tickets?"
A5: "Check-in (/api/v1/checkins) requires the 'organizer' role.
 Payment confirmation (/api/v1/payments/merchandise/manual) requires either 'treasurer' or 'organizer' roles.
 Ordinary members and volunteers receive HTTP 403 Forbidden. Unauthenticated requests receive HTTP 401 Unauthorized. CSRF tokens are strictly validated on all state-changing POST requests."

Q6: "How did you test your work?"
A6: "We wrote real integration API tests in server/tests/merchandise-payment.api.test.js using Node.js native test runner and Supertest-equivalent fetch client. The suite tests:
 - RBAC & CSRF rejection
 - Payload mismatch & idempotency replays
 - Concurrent payment attempts
 - Concurrent cancellation vs payment races
 - Paid-order cancellation rejection
 - Regression tests ensuring event ticket payments still function properly."
